## 5. Decision-engine architecture verification

The runtime now follows this ordering:

```text
hard sensor thresholds → relay/fail-safe logic
ML → classification/supporting intelligence
rule engine → fallback when ML is unavailable or uncertain
```

### XGBoost primary

- XGBoost probabilities are the only classifier probabilities assigned to
  `classifierProbs`.
- `finalClass` is initialized from the XGBoost top class.
- The final ML label is derived from the XGBoost class when confidence is
  sufficient.
- Low-confidence XGBoost output abstains to `Anomaly Detected`, as required by
  the uncertainty fallback path.

Live verification showed a non-threshold anomaly with:

```text
XGBoost top class: Bearing Wear
RF top class:      Normal
IF anomaly score:  0.5732
IF threshold:      0.567
Final response:    Anomaly Detected
Confidence:        0.3831
Override:          false
```

This is the expected uncertain-ML fallback: XGBoost was the primary classifier,
but its confidence was below the minimum classification confidence. The RF
prediction did not replace it.

### Random Forest shadow-only

Random Forest is executed for comparison and monitoring only. Its top class is
returned in `rfTopClass`, disagreement is logged, and `modelsAgreed` is
reported. There is no RF probability fusion or RF-based final-class branch.

A live disagreement was observed repeatedly:

```text
RF shadow class:    Normal
XGBoost primary:    Bearing Wear
classifierDisagreement: true
```

The API logs this as:

```text
[DE] RF shadow disagreement with XGBoost primary
```

RF did not change the final label, confidence, severity, health score, relay
decision, or override decision.

### Isolation Forest anomaly gate

The Isolation Forest ONNX label is converted to the runtime anomaly gate:

- inlier → normal-side score
- outlier → fault-side score
- score threshold is read from `preprocessing.json` (`0.567`)

For the healthy live case, the Isolation Forest score was `0.5621`, below the
loaded threshold, and the ML path correctly bypassed classifier fault output
with `faultLabel: "Normal"`.

For the non-threshold anomaly case, the score was `0.5732`, above the loaded
threshold, so the classifier path ran.

### Rule-engine and relay fail-safe

The sensor threshold/rule engine remains independent of ML:

- High THD, High Vibration, Overcurrent, and Phase Imbalance are produced by
  sensor/rule logic when their thresholds are met.
- These are not falsely represented as trained ML classes.
- Hard relay conditions override ML and force the relay-trip result.
- ML unavailability or uncertainty falls back to rule-engine classification.
